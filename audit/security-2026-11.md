## 1. Локальные порты

### PT-01. SOCKS5 без пароля в расширении — Высоко

**Где**: `Packages/TunnelCore/Sources/TunnelCore/XrayBacked.swift`, `runtime(_:portBase:)`: на каждый сервер,
который ведёт Xray-core, создаётся inbound `"listen": "127.0.0.1", "port": 20800 + i, "protocol": "socks",
"settings": {"auth": "noauth", "udp": true}`. Запуск — `PacketTunnel/PacketTunnelProvider.swift`, `startXray`;
sing-box подключается к нему через `XrayBacked.socks(tag:port:)` тоже без логина. Порты постоянные
(`tunnelPortBase = 20800`).

**Когда открыт**: пока работает туннель, если выбранный сервер ведёт Xray-core: маски `finalmask`, `sudoku`,
VLESS REALITY поверх gRPC (с 3.1.14 такие серверы всегда переносятся в Xray). При автовыборе порт открыт, если
такой сервер есть в подписке.

**Чем грозит**: loopback в iOS общий для всех процессов, песочница не мешает приложению подключиться к
127.0.0.1. Любое приложение (мессенджер, SDK аналитики, банковское приложение) может:
- обнаружить VPN — порт 20800 отвечает как SOCKS5;
- узнать внешний IP сервера: сделать через этот SOCKS запрос к любому сервису «мой IP»;
- пускать через сервер владельца свой TCP и UDP (UDP ASSOCIATE включён). Это расходует лимит подписки, а
  действия идут от IP сервера.
Авторизации нет. Ограничивает только `"ip": "127.0.0.1"` (адрес для UDP), то есть ничего. Ровно этот класс
уязвимостей в 2025 году нашли у Xray-клиентов для iOS и Android.

**Как исправить**:
1. Пароль: на каждый запуск генерировать случайные логин и пароль (`SecRandomCopyBytes`, ≥128 бит). В inbound
   Xray — `"auth": "password", "accounts": [{"user": …, "pass": …}]`, в outbound sing-box — `"username"`,
   `"password"`. Хранить только в памяти и в `tunnel-xray.json`/`tunnel.json`, сразу с `Redactor` для этих полей.
2. Случайный порт из динамического диапазона на каждый запуск вместо 20800+i. Иначе порт выдаёт VPN даже с
   паролем (сканер видит SOCKS5, который требует логин).
3. Тест в TunnelCore: в runtime нет `noauth`, у outbound sing-box и inbound Xray одинаковые учётные данные;
   образец в `tunnelcore-fixtures`.
4. Дальше: убрать TCP-листенер вообще. Xray умеет слушать Unix-сокет (`"listen": "/path/x.sock"`), но SOCKS-outbound
   sing-box к Unix-сокету не подключается. Нужна правка в форке ядра (dialer к `unix:`) — предложить отдельно.

**Проверено по коду**: да. **Только на устройстве**: что стороннее приложение действительно достаёт до порта
(достаточно тестового приложения с `NWConnection` к 127.0.0.1:20800).

### PT-02. То же в ядре приложения во время пинга — Средне

**Где**: `App/Sources/Core/LatencyService.swift`, `LocalCoreProbes.start`: на каждую подписку с Xray-серверами
поднимается Xray с SOCKS без пароля на `30800 + 500·индекс + i` (`XrayBacked.appPortBase`). Сюда попадают
**все** Xray-серверы **всех** подписок. Закрывается в `close()` по окончании проверки.

**Чем грозит**: то же, что PT-01, но окно короче (секунды–минуты пинга) и только пока приложение на экране.
Порт ведёт через любой из серверов, а не только через выбранный.

**Как исправить**: так же, как PT-01 (общий код `XrayBacked.runtime` — исправится одним изменением).

### Что в порядке

- **Командный сервер libbox** (`LibboxNewCommandServer`): в закреплённом ядре
  (`experimental/libbox/command_server.go`) он слушает TCP только при `CommandServerListenPort ≠ 0`. Приложение
  этот параметр не задаёт, поэтому сервер — Unix-сокет в корне App Group. Доступ к нему есть только у процессов
  с этой группой. Секрета (`CommandServerSecret`) нет, но при Unix-сокете в группе он и не нужен.
- **Clash API и V2Ray API** в сборку не входят: тегов `with_clash_api` и `with_v2ray_api` нет в `BUILD_TAGS`, раздела
  `experimental` в конфигурации нет (`ConfigBuilder.build`).
- **Inbound у sing-box** только `tun`, без `mixed`/`socks`/`http`; HTTP-прокси системы не включается
  (`isHTTPProxyEnabled` в `TunnelPlatform` срабатывает только при `platform.http_proxy`, которого нет).
- Из Xray-конфигураций подписки берутся только `outbounds` (`XrayBacked.node`). Свои inbound провайдер добавить не
  может. Серверы на 127.0.0.1/localhost отбрасываются.
- **Только на устройстве (низкий риск)**: стек `mixed`/`system` в sing-tun слушает TCP на адресе TUN
  (172.19.0.1, случайный порт) и принимает только соединения из своей таблицы NAT. Стоит один раз проверить, что
  прямое подключение к этому порту из другого приложения сразу закрывается.

## 2. Утечки и kill switch

### PT-06. Серверы всех подписок идут мимо VPN для всех приложений — Средне

**Где**: `ConfigBuilder.build`: из `options.serverHosts` (заполняется в `LibraryStore.writeActiveConfig` адресами
серверов **всех** подписок, до 4000) делаются правила `{"domain": […], "outbound": "direct"}` и
`{"ip_cidr": [/32, /128], "outbound": "direct"}`. Они стоят первыми, до `sniff`/`hijack-dns`. Плюс
`dns.reverse_mapping`. Нужно это для пинга серверов ядром приложения при включённом VPN.

**Чем грозит**: правило действует не только на пинг приложения, а на любой трафик устройства. Если сервер указан
«чистым IP» CDN (частая схема VLESS-WS/xhttp через Cloudflare) или популярным доменом, то все сайты на этом
адресе anycast и сам домен открываются напрямую, с настоящим IP, мимо VPN. Пользователь этого не видит.

**Как исправить**: вернуть пинг на физический интерфейс, а не открывать дыру в туннеле:
- в `ConfigBuilder.probe` указать прямому соединению физический интерфейс (`route.default_interface` или
  `bind_interface` у серверных outbound — имя интерфейса уже вычисляется в `PacketTunnelProvider.physical`;
  в приложении — через `NWPathMonitor`, так же как `NetworkProbes` с `prohibitedInterfaceTypes = [.other]`);
- правила `serverHosts` из конфигурации туннеля убрать, а при kill switch (обход невозможен) пинговать через туннель;
- если обход оставить, то хотя бы только на время проверки (перезагрузка конфигурации до и после) и без
  IP-диапазонов известных CDN. Тест в TunnelCore на состав правил.
**Проверено по коду**: да. **На устройстве**: что пинг ядром приложения с привязкой к интерфейсу работает при VPN.

### PT-07. Смена сервера — полная остановка VPN — Средне

**Где**: `App.select` → `reconnect()` → `TunnelController.stop()` (выключает On Demand, `stopVPNTunnel`), затем
запуск заново. Расширение в `stopTunnel` с `.userInitiated` тоже выключает On Demand.

**Чем грозит**: при выключенном kill switch (так по умолчанию, PT-08) несколько секунд между остановкой и
«подключено» весь трафик идёт напрямую. Приложения в фоне (мессенджеры, push-клиенты) переподключаются с
настоящим IP, а сайт или сервис видит оба адреса подряд.

**Как исправить**: менять сервер перезагрузкой конфигурации в работающем туннеле. Механизм уже есть:
`TunnelController.reload` → `handleAppMessage(reload)` → `startOrReloadService`, туннель остаётся поднят,
`reasserting = true`. Полную остановку оставить на случай, если перезагрузка не удалась.
**На устройстве**: есть ли окно при `startOrReloadService` (ожидается: пакеты ждут или теряются, но мимо не идут).

### PT-08. Kill switch выключен по умолчанию; поведение при сбоях — Средне

**Где**: `Prefs.killSwitch` = `false` по умолчанию; `TunnelController.configure`: `includeAllNetworks =
Prefs.killSwitch`, `excludeAPNs = true`, `excludeCellularServices = true` (iOS 16.4+); `enforceRoutes =
Prefs.secureDNS` (по умолчанию `false`). При ошибке запуска `TunnelController.sync` вызывает `disableOnDemand()`.
С kill switch `ConfigBuilder.stackForIncludeAllNetworks` переключает стек на gVisor, без него стек `mixed`.

**Чем грозит**:
- **Без kill switch** (по умолчанию) трафик идёт мимо туннеля, когда расширения нет: от гибели по лимиту памяти до
  перезапуска On Demand, при смене сервера (PT-07), после неудачного запуска (On Demand выключается, VPN так и
  остаётся выключенным, пользователь видит только сообщение). Соединения, открытые до запуска VPN, iOS не рвёт, и
  они продолжают идти напрямую.
- **С kill switch** iOS сама не выпускает трафик, пока туннель поднимается или переподключается. Стек gVisor на
  защиту не влияет — он только разбирает пакеты внутри туннеля. В смешанном стеке разницы для утечек нет: оба
  стека получают пакеты из одного utun, обход решают маршруты iOS, а не стек.
- **Даже с kill switch** мимо идут APNs и службы оператора (`excludeAPNs`, `excludeCellularServices`): Apple и оператор
  видят настоящий IP. Это осознанный компромисс (без них не работают push и VoLTE/SMS), его стоит описать в подписи
  к переключателю.
- После неудачного запуска с kill switch VPN выключается. Блокирует ли iOS трафик в таком «выключенном» состоянии —
  неизвестно, проверить на устройстве.

**Как исправить**: (решение владельца) предложить kill switch включённым для новых установок или спросить при
первом подключении. После неудачного запуска не выключать On Demand молча: показывать, что защиты нет, или
повторять запуск один раз. В подписи к kill switch назвать исключения (push, оператор).
**Только на устройстве**: всё поведение `includeAllNetworks` — смерть расширения (jetsam), перезапуск системой, On
Demand, неудачный старт, режим полёта и смена Wi-Fi/LTE.

### PT-09. Прямой DNS — Низко–средне

**Где**: `ConfigBuilder.directResolvers`: `dns-direct` — группа UDP-резолверов `[выбранный, 77.88.8.8, 8.8.8.8]`
в режиме `parallel`, мимо туннеля. Через неё разрешаются адреса серверов (иначе туннелю не подключиться), домены из
`serverHosts` (PT-06) и российские домены при обходе для российских сайтов (по умолчанию включён).

**Чем грозит**: имена серверов VPN уходят открытым UDP — провайдер и ТСПУ видят, к какому VPN-домену подключается
устройство, и могут заблокировать его по DNS. Каждый такой запрос уходит в Яндекс и Google, даже если пользователь
выбрал другой резолвер.

**Как исправить**: для `dns-direct` использовать DoH/DoT по IP (`"type": "https", "server": "1.1.1.1"` без detour —
идёт напрямую, но зашифрованно); набор запасных резолверов сделать настройкой, а не константой; Яндекс не добавлять
без выбора пользователя. Тест на состав `dns.servers`.

### PT-10. Обход для российских сайтов и сопоставление адресов — Инфо

**Где**: `ConfigBuilder.build`, `bypassRussia` (по умолчанию `true`): правила `pt-ru-*` → `direct`, их DNS → `dns-direct`.

**Чем грозит**: так задумано, но это известный способ деанонимизации. Любой сайт может встроить ресурс с
российского домена или IP (или STUN-сервер для WebRTC) и увидеть настоящий IP рядом с IP VPN. Российские
приложения так и определяют VPN. Это не ошибка, но в описании переключателя стоит об этом сказать.

### PT-11. IPv6 и WebRTC — Инфо

- **IPv6**: у TUN есть адрес `fdfe:dcba:9876::1/126` (`ConfigBuilder.build`), `TunnelPlatform.networkSettings` ставит
  маршрут IPv6 по умолчанию, если ядро передало адрес IPv6. Значит, IPv6 заворачивается в туннель и мимо не идёт.
  Слабое место — условие `if !v6.isEmpty`: без адреса IPv6 в конфигурации маршрута IPv6 не будет, и IPv6 пойдёт
  напрямую. Стоит закрепить тестом в TunnelCore, что адрес IPv6 у `tun-in` есть всегда.
- **DNS**: `hijack-dns` и DNS-сервер TUN; DoH/DoT/DoQ приложений блокируются при блокировке рекламы
  (`blockEncryptedDNS`) — так их запросы тоже идут через туннель.
- **WebRTC/STUN**: UDP идёт через TUN, а `strict_route` на iOS ни на что не влияет. Утечка возможна в двух
  случаях: кандидаты host (локальные адреса, в том числе публичный IPv6 физического интерфейса) и STUN на российский
  IP при обходе (PT-10). **Проверить только на устройстве**, например на browserleaks.com/webrtc в Safari и Chrome,
  с обходом и без.

## 3. Подписки

### PT-12. Загрузка по http — Низко

**Где**: `SubscriptionService.fetch` и `App.add(text:)` принимают `http` наравне с `https`. В `Info.plist` нет
`NSAppTransportSecurity`, поэтому действует ATS: URLSession не загрузит `http://` по имени и не пойдёт по
редиректу с https на http — запрос упадёт с ошибкой ATS.

**Чем грозит**: сейчас ATS спасает (подписка с секретом в пути открытым текстом не уйдёт), но:
- пользователь видит непонятную системную ошибку, а не «http запрещён»;
- если кто-то добавит исключение ATS «чтобы заработало», подписка и заголовки HWID пойдут открытым текстом;
- для `http://IP` (без имени) поведение ATS нужно проверить на устройстве.

**Как исправить**: явно отказывать в `http://` до запроса с понятным текстом (или предупреждать и никогда не
отправлять заголовки устройства по http). В `URLSessionTaskDelegate.willPerformHTTPRedirection` запретить смену
схемы на http. Тест на разбор адреса подписки.

### PT-13. Заголовки устройства и подмена User-Agent — Средне

**Где**: `SubscriptionService.fetch`: перебор User-Agent `INCY/2.7.2` → `Happ/3.13.0` → `PersonalTunnel/2.0`. С
INCY и Happ, если `sendIdentity`, уходят `X-HWID`, `X-Device-OS: iOS`, `X-Ver-OS` (версия iOS), `X-Device-Model`
(`utsname.machine`, например iPhone17,1), `X-Device-Locale`. HWID — `DeviceIdentity`: первые 32 hex
`identifierForVendor` (или сохранённый из 1.x). Для Xray JSON второй запрос без заголовков устройства (`plainList`).

**Чем грозит**:
- **Первое добавление всегда с заголовками**: `App.add(text:)` вызывает `fetch(…, sendIdentity: true)`. Переключатель
  «Отправлять HWID» появляется только у уже добавленной подписки, то есть отказаться заранее нельзя. Любая ссылка
  (QR, буфер) сразу отправляет хозяину адреса HWID, модель, версию iOS и язык.
- **Один HWID для всех панелей**: владельцы разных панелей (или одна компания за несколькими) могут сопоставить
  устройство. HWID — это IDFV, общий для всех приложений одного разработчика.
- **Редиректы**: URLSession переносит заданные вручную заголовки в запрос после редиректа, в том числе на другой
  хост. Панель за CDN или с перенаправлением раскрывает HWID третьей стороне (подтвердить на устройстве).
- **Подмена User-Agent** под Happ/INCY: панель отдаёт конфигурации, рассчитанные на тот клиент, и считает устройство
  устройством Happ. Для безопасности это не дыра, но это обман провайдера, а версии зашиты в код — панели могут
  начать отличать клиент по другим признакам.

**Как исправить**:
- экран подтверждения при добавлении (см. PT-14) с переключателем «Отправлять HWID и данные устройства» и
  именем хоста;
- (решение владельца, ключи 1.x не трогать) для **новых** подписок — HWID на хост: `HMAC-SHA256(hwid, host)`, первые
  32 hex. Существующие подписки продолжают отправлять старый HWID, чтобы панели не увидели новое устройство;
- в делегате редиректа убирать `X-HWID`/`X-Device-*` при смене хоста и запрещать https → http;
- `X-Device-Locale` и `X-Ver-OS` отправлять только тем панелям, которые без них не отдают серверы (или вовсе не
  отправлять).

## 4. Сертификаты

### PT-03. Обход закрепления `certificate_sha256` — Высоко

**Где**: `core/patches/0003-certificate-sha256-pin.patch`: `VerifyCertificateSHA256` принимает соединение, если хэш
**любого** сертификата из присланной сервером цепочки совпал с закреплённым; при этом `InsecureSkipVerify = true`, а
проверка имени отключена. Подключается в `std_client.go` и `utls_client.go`. Закреп берётся из ссылок
(`pcs`, `pinnedPeerCertSha256`, `pinSHA256` — `CertificatePins.carry`, `StreamSettings`).

**Чем грозит**: закреплённый сертификат не секрет — сервер присылает его при каждом рукопожатии. Атакующий на
пути (Wi-Fi, провайдер, ТСПУ) отвечает цепочкой «свой самоподписанный leaf + настоящий закреплённый
сертификат». Подпись CertificateVerify проверяется ключом leaf, то есть ключом атакующего, а связь leaf с
закреплённым сертификатом никто не проверяет. Рукопожатие проходит, атакующий получает трафик Hysteria2 (пароль
`auth`) или VLESS/Trojan поверх TLS, то есть пароль и UUID. Это касается всех серверов с закрепом, которые ведёт
sing-box. Самоподписанные серверы с `pinSHA256` встречаются часто, и для них закреп — единственная защита.

**Проверено в песочнице**: Go 1.24, `crypto/tls`, функция проверки скопирована из патча, сервер отдаёт
`[свой leaf, настоящий сертификат]`:

```
MITM handshake with pinned cert appended, error = <nil>
```

Комментарий в патче («as in Hysteria and Xray») верен только для Hysteria. В закреплённом Xray-core
(`transport/internet/tls/config.go`, `verifyChain`) совпадение с leaf принимается сразу, а совпадение с
сертификатом выше по цепочке — только если он CA и leaf действительно им подписан (`foundCA` → `x509.Verify`).
Так что серверы, которые ведёт Xray-core, этой уязвимости не имеют.

**Как исправить** (в патче 0003, с тестом в `certificate_pin_lx_test.go`):
1. Совпадение с `rawCerts[0]` (leaf) — принять.
2. Совпадение с другим сертификатом — принять, только если он `IsCA` и `leaf.Verify` с ним как единственным корнем
   (и промежуточными из цепочки) успешен. Это поведение Xray.
3. Тест: цепочка `[чужой leaf, закреплённый сертификат]` отвергается — и в стандартном движке, и в uTLS.
Отпечатки ключа (`certificate_public_key_sha256`, код upstream) проверяют только leaf — там всё в порядке.

### PT-04. `allowInsecure` / `insecure` — Средне

**Где**: `ShareLinks` (`allowInsecure`, `insecure`, `allow_insecure`), `XrayImport` (`allowInsecure` →
`tls.insecure`), редактор `ServerDraft`. sing-box выполняет `insecure: true` без всякой проверки сертификата и имени. В
интерфейсе это видно только в карточке сервера («не проверяется», `ServerInspection`).

**Чем грозит**: такие серверы открыты для MITM так же, как в PT-03, только без всякого обхода. Провайдеры Xray
часто раздают `allowInsecure=1`, и пользователь не знает, что его сервер не проверяется.

**Как исправить**: отметка «сертификат не проверяется» в списке серверов и в сводке импорта. Если у сервера есть
и закреп, и `insecure`, `StreamSettings.tls` записывает оба поля. По коду патча закреп всё равно проверяется (Go
вызывает `VerifyPeerCertificate` и при `InsecureSkipVerify`), но это стоит закрепить тестом ядра.
**Попутно (не безопасность)**: `XrayBacked.apply` пишет `"allowInsecure": true` в Xray-конфигурацию, а закреплённый
Xray-core v26.11.9 отвергает это поле как удалённое (`PrintRemovedFeatureError` в
`infra/conf/transport_security.go`). Сервер Xray, отредактированный с «не проверять», уронит запуск всего Xray-core
в туннеле. Лучше переводить такое поле в `pinnedPeerCertSha256` или не давать его выбрать.

### PT-05. Свой центр сертификации и общий корень — Инфо (в порядке)

- CA из подписки (`tlsSettings.certificates`, `usage: verify` → `tls.certificate` в `StreamSettings`/`XrayImport`)
  кладётся в TLS конкретного outbound. В sing-box это корни только для этого соединения, с проверкой имени. Для
  Xray-серверов CA тоже остаётся в своём outbound. Общего хранилища доверия он не трогает
  (`"certificate": {"store": "mozilla"}` в `ConfigBuilder` от подписки не зависит), загрузку подписок в
  `URLSession` (своего `SecTrust`/делегата проверки нет) и системное хранилище iOS тоже. Подменить другие
  соединения через такой CA нельзя.
- CA задаётся только если нет `insecure` и закрепов — это правильно.
- Мелочь: `LDFLAGS` в `scripts/build-libbox.sh` содержат `runtime.godebugDefault=…tlssha1=1` — возвращает подписи
  SHA-1 в рукопожатии TLS 1.2. Ради совместимости со старыми серверами это допустимо, но стоит записать, зачем это
  нужно, и убрать, когда станет не нужно. **Низко.**

## 5. Хранение

### PT-15. Ключи и ссылки в файлах App Group и в бэкапе — Средне

**Где и что**:

| Что | Где | Защита | В бэкапе |
|-----|-----|--------|----------|
| Все подписки (ссылки с токенами), серверы с ключами | `App Group/PersonalTunnel/library.json` (`LibraryStore.save`) | `completeUntilFirstUserAuthentication` | да |
| Конфигурация туннеля (ключи выбранного сервера) | `…/PersonalTunnel/tunnel.json`, `tunnel-xray.json` | то же | да |
| Копия конфигурации от ядра | `App Group/configuration.json` — libbox `saveConfigSnapshot` при каждом запуске, права `0666` | класс по умолчанию (C) | да |
| Копии конфигурации в отчётах о падении и OOM | `App Group/Library/Caches/Working/crash_reports/*/configuration.json` (`copyConfigSnapshot`) | C | нет (Caches) |
| Данные 1.x | `App Group/settings.db`, `configs/` — после миграции не удаляются | C | да |
| HWID | Keychain `AfterFirstUnlockThisDeviceOnly` (хорошо) **и** копия в `UserDefaults.standard` | C | копия в UserDefaults — да |
| Резервная копия из настроек | `tmp/PersonalTunnel-….ptbackup.json` | C | нет, но после экспорта не удаляется |

**Чем грозит**: ключи и ссылки подписок в открытом JSON. После первой разблокировки их может прочитать любой код,
у которого есть доступ к файлам приложения. Они попадают в бэкап iCloud (у Apple есть ключи без «Расширенной
защиты данных») и в бэкап Finder/iTunes (без шифрования — открытым текстом). Копии конфигурации от ядра лежат даже
после удаления подписки. Через копию HWID в UserDefaults он переезжает на новое устройство при восстановлении из
бэкапа — возможно, так и задумано (панели видят «то же» устройство), но Keychain `ThisDeviceOnly` этого как раз
не позволяет.

**Как исправить** (по степени вмешательства):
1. `isExcludedFromBackup` для `PersonalTunnel/` и `configuration.json` — решение владельца: после восстановления
   подписки придётся добавить заново или восстановить из своей копии.
2. `library.json` читает только приложение — можно класс `.completeUnlessOpen`. `tunnel.json` должен оставаться C:
   On Demand запускает расширение при заблокированном экране.
3. Снимки конфигурации ядра: в форке отключить `saveConfigSnapshot`/`copyConfigSnapshot` для iOS (патч, как 0002)
   или пропускать конфигурацию через вырезание секретов. Чистить `crash_reports` старше N дней.
4. Удалять `settings.db`/`configs/` 1.x после успешной миграции и одного запуска 2.x — решение владельца (сейчас их
   намеренно не трогают).
5. Удалять временный файл резервной копии после экспорта (`UIDocumentPickerDelegate` → `removeItem`).
6. Перенос секретов (ключей и токенов подписок) в Keychain — большая работа, имеет смысл только вместе с п. 1.

**Проверено по коду**: да. **На устройстве**: фактический класс защиты файлов, которые пишет Go (`os.WriteFile`), и
состав бэкапа (зашифрованный бэкап Finder + iMazing/`idevicebackup2`).

## 6. URL-схема, буфер, QR, файлы

### PT-14. Импорт без подтверждения — Низко

**Где**: `AddServerFlow` в `App/Sources/Shared/Pages.swift`: буфер, ввод, QR, файл → сразу `App.add(text:)`.
Для адреса подписки сразу уходит запрос с заголовками устройства (PT-13), подписка добавляется, а если активной не
было — становится активной.

**URL-схема**: `personaltunnel://` (или `ptbeta://`) объявлена в `Info.plist` (`CFBundleURLTypes`), но обработчика
нет: в `SceneDelegate` нет `scene(_:openURLContexts:)`, а `connectionOptions.urlContexts` не читаются. Чужая ссылка
сейчас только открывает приложение и ничего не добавляет. **Тихого импорта нет.**

**Буфер** читается только по нажатию «Вставить из буфера обмена» (iOS спросит разрешение). Само приложение кладёт
в буфер ссылки серверов и подписок (`copySelected`, `ServerInspector.copy`): через Universal Clipboard они уходят на
Mac и остаются в буфере.

**Чем грозит**: прямой уязвимости нет — каждое добавление начинает сам пользователь. Но QR с чужой подпиской
(плакат, подмена картинки) сразу раскрывает данные устройства хозяину адреса.

**Как исправить**: экран подтверждения перед добавлением — тип, хост (без пути и токена), число серверов, переключатель
HWID. Сетевой запрос — только после «Добавить». Если URL-схема когда-нибудь будет обрабатываться — только через этот
экран; если не планируется — убрать `CFBundleURLTypes`, иначе схему может занять другое приложение и ловить ссылки.
Ссылки класть в буфер с `UIPasteboard.general.setItems(…, options: [.localOnly: true, .expirationDate: …])`.
Восстановление из резервной копии заменяет всю библиотеку — спрашивать подтверждение.

## 7. Журналы

### PT-16. Пробелы `Redactor` и посещённые домены в журнале — Средне

**Как устроено**: `Redactor.redact` (`Packages/TunnelCore/Sources/TunnelCore/Redactor.swift`) прячет ссылки известных
схем, `https?://хост/путь`, значения после `uuid|password|…|short_id|secret`, UUID. «Скопировать всё» в журнале
(`ServiceLogViewController.copyAll`) добавляет `hideServers` — имена серверов и IP в строках, где эти имена есть.
Через Redactor идут ошибки запуска (`lastTunnelError`), события расширения (`TunnelEvents`), отчёт о падении
(`CrashReportViewController.shareText` — с `hideServers`), сообщения пинга (`hideAddresses`).

**Что проходит насквозь** (те же выражения в Python):

| Вход | После Redactor |
|------|----------------|
| `socks4://user:SECRET@…`, `http-proxy://…`, `https-proxy://…` | без изменений — этих схем нет в правиле, хотя `ShareLink.schemes` их поддерживает |
| `"peer_public_key":"…"` | без изменений — `\b` не срабатывает после `_` |
| `Authorization: Bearer SECRET` | `Authorization: *** SECRET` — токен остался |
| `{\"password\":\"SECRET\"}` (JSON внутри строки ошибки) | без изменений |
| `"username":"…"` (naive, socks, http) | без изменений |
| `"id":"произвольная-строка"` (Xray допускает не-UUID id) | без изменений |
| `pbk=…&sid=…` вне ссылки (фрагмент в ошибке) | без изменений |
| `outbound connection to 203.0.113.7:443` | IP остаётся, если в строке нет имени сервера |
| `inbound connection to сайт.пример:443` | без изменений |

**Чем грозит**:
- пароли socks/http-прокси, токены и части ключей могут попасть в скопированный журнал и в отчёт;
- **история посещений**: уровень журнала по умолчанию `info` (`TunnelOptions.logLevel`), и sing-box пишет каждое
  соединение с доменом назначения. «Скопировать всё» отдаёт список сайтов, которые пользователь открывал.
  Пересылая журнал для диагностики, человек раскрывает историю браузера;
- IP сервера остаётся, если строка называет только адрес (Xray: `dial tcp IP:порт`), а сервер задан доменом;
- `copyReport` («Скопировать отчёт» на странице диагностики) не вызывает `hideServers`.

**Что в порядке**: файл `configuration.json` в папках падений в копию не попадает: `lastCrash` читает только
`go.log` и `CrashReport-packet-tunnel.log`. Журнал Xray в расширении — уровень `warning`, `access: none`;
журнал пинга Xray во временной папке удаляется в `close()`.

**Как исправить** (с тестами в `TunnelCore`, обязательно — это разбор текста):
- добавить в правило ссылок `socks4|http-proxy|https-proxy|hysteria|juicity|…` — лучше строить список из
  `ShareLink.schemes` + `rejected`, чтобы новые схемы не забывались;
- ключи: `(?<![A-Za-z0-9])` вместо `\b` перед именем поля; `username|user|pbk|sid|obfs[_-]?password|id`;
  экранированные кавычки `\\?"`; `Bearer\s+\S+`;
- для копирования журнала: заменять назначения в строках `connection to X:port` на `<назначение>` (или на
  eTLD+1 по желанию пользователя); IP-адреса прятать во всех строках, кроме адресов TUN;
- в `copyReport` — тоже `hideServers`;
- по умолчанию предлагать уровень `warn` (или переключать на `info` только на время диагностики).

## 8. Сборка

### PT-17. Цепочка поставки — Низко

**В порядке (проверено по коду)**:
- sing-box-lx и Xray-core клонируются по тегу, а затем **коммит сверяется** с `SING_BOX_COMMIT`/`XRAY_COMMIT` из
  `core/VERSION` (`scripts/core-env.sh`, `fetch_core`/`fetch_xray`); при расхождении сборка падает. Подмодули
  sing-box берутся по коммитам, записанным в закреплённом коммите. Патчи — из репозитория.
- Go-модули моста сверяются по `core/bridge/go.sum`; `gomobile`/`gobind` ставятся `go install …@v0.1.12` через
  sumdb; нужная версия Go скачивается через `GOTOOLCHAIN`, тоже с проверкой sumdb. `GOFLAGS`/`GONOSUMDB`/`GOPROXY` не
  переопределены.
- В workflow нет секретов, `permissions: contents: read`, IPA не подписывается в CI. Списки правил сверяются с
  `SHA256SUMS`. Прошлый поиск секретов в истории — `audit/history-scan-2026-11-12.txt`.

**Слабые места**:
1. Actions закреплены тегами, а не SHA: `actions/checkout@v4`, `actions/cache@v4` (`/restore`, `/save`),
   `actions/setup-go@v5`, `actions/upload-artifact@v4`. Все от GitHub, поэтому риск ниже, чем у сторонних, но
   перенос тега выполнит чужой код с доступом к исходникам и артефакту IPA. **Исправить**: закрепить по полному
   SHA с комментарием о версии, обновлять через Dependabot.
2. `brew install xcodegen` — последняя версия, без закрепа; xcodegen генерирует проект, из которого собирается IPA.
   **Исправить**: закрепить версию (скачать релиз с SHA256 или `mint`/`brew` с конкретной формулой).
3. `docker run … swift:6.1` — тег, а не digest. Влияет только на тесты, в IPA не попадает. **Исправить**: `swift:6.1@sha256:…`.
4. `AppCore.xcframework` и `Libbox.xcframework` берутся из `actions/cache` и **попадают в IPA**. Ключ кэша
   предсказуем. Записать кэш может любой запуск workflow в этом репозитории (ветки `claude/**`). Кэш веток не виден
   `main`, но ветка видит кэш `main`. Чужих участников в репозитории нет, поэтому риск низкий. **Исправить**: в
   релизных сборках собирать ядра без кэша или сверять `CORE.txt` + SHA256 фреймворка с записью в репозитории.
5. `SHA256SUMS` считается в той же задаче, что и IPA: это проверка целостности при скачивании, а не подлинности.
   Для подписи вне CI этого достаточно, но в `source-commit.txt` уже есть коммит — можно добавить attestation
   (`actions/attest-build-provenance`).
6. Списки правил (`scripts/update-ad-lists.sh`) качаются с веток `main` HaGeZi и AdGuard, без закрепа коммита.
   `SHA256SUMS` проверяет только то, что лежит в репозитории. Подменённый список `ru-*` пустил бы домены мимо VPN.
   Риск низкий: обновление ручное, изменения видны в diff. Стоит записывать в NOTICE коммит источника.
7. `actions/checkout` оставляет токен в `.git/config` (`persist-credentials` по умолчанию). При `contents: read`
   это неважно, но можно поставить `persist-credentials: false`.
